# Финальный чистый прогон (имитация проверки жюри)

Задача исполнителя: сыграть роль эксперта жюри, который впервые видит репозиторий. Пройти ПОРЯДОК ПРОВЕРКИ из кейса (установка → BASE → MANDATORY_STRESS → дополнительные тесты → сравнение → выгрузка) на ЧИСТОМ клоне, не имея ничего, кроме git и интернета. Любое отклонение от заявленных в README чисел или любая неработающая команда — блоккер, фиксируется в отчёте.

Важно: прогон делается на устройстве/в директории, которые НЕ участвовали в разработке (никаких локальных артефактов, кэшей, venv от прошлых волн). Ничего в репозитории не менять и не коммитить — это аудит, а не разработка.

Скопируйте текст ниже первым сообщением в новую сессию модели.

---

```text
Ты — независимый аудитор финальной сборки проекта «Топливный космоконтур 2035» (КосмоХакатон, кейс 2). Твоя роль — эксперт жюри, который впервые получил репозиторий и проходит порядок проверки строго по README и docs/ИНСТРУКЦИЯ.md. Ты НЕ разработчик: тебе запрещено что-либо чинить, изменять или коммитить. Ты только проверяешь и честно фиксируешь результаты.

## Подготовка (чистая среда)

1. Создай НОВУЮ пустую рабочую директорию (например clean_run_<дата>), отличную от любых существующих клонов проекта. Внутри неё:
   git clone git@github.com:l1ttleFox/sad9ugn.git repo
   (если SSH недоступен — https://github.com/l1ttleFox/sad9ugn.git)
2. cd repo; git log --oneline -1 — запиши commit (это «версия под аудитом»).
3. Создай изолированное виртуальное окружение (python -m venv .venv; активируй; pip install -r requirements.txt). Зафиксируй версии Python и pip. Установка должна пройти БЕЗ ручных доустановок; если что-то падает или требует пакет вне requirements.txt — это блоккер B-INSTALL.
4. Убедись, что в репозитории нет секретов: быстрый просмотр на токены/ключи/пароли (grep по очевидным паттернам token/api_key/password/secret/BEGIN.*PRIVATE KEY). Найденное — блоккер B-SECRET.

## Шаг 1 — Стандартный сценарий (BASE)

5. Прогони тесты: python -m pytest tests/ -q. Ожидаемо: все зелёные (зафиксируй точное число passed). Падение — блоккер B-TESTS.
6. Контрольные векторы: python tests/run_control_checks.py. Ожидаемо 10/10 OK. Иначе — блоккер B-V01.
7. Открой README.md, раздел порядка проверки, шаг 1 (BASE). Выполни ровно указанные команды/действия (включая ожидаемые числа: PV ≈ 9961.31, SL = 1.000, резерв на начало года ≥ порога 45 дней, 0 hard-нарушений). Сверь фактические числа с ожидаемыми в README (допуск — точность отображения, не «примерно похоже»). Расхождение — блоккер B-BASE-NUM.
8. Запусти UI: python -m streamlit run app/main.py --server.headless true --server.port 8501. Сервер должен стартовать без ошибок. Затем закрой. Падение — блоккер B-UI-START.
9. По docs/ИНСТРУКЦИЯ.md пройди пользовательский сценарий (если доступен программный способ — Streamlit AppTest/pytest UI-тесты — используй его и зафиксируй): загрузить контрольный набор → открыть FINAL_BASE → изменить решение (заказ/резерв/инвестиция) → пересчитать → увидеть нарушения с годом/величиной/причиной → вернуть исходный план. Каждый неработающий шаг — отдельный блоккер B-UI-STEP с номером шага.

## Шаг 2 — Обязательный стресс (MANDATORY_STRESS)

10. По README шаг 2: открой FINAL_STRESS / переключи сценарий, выполни указанные команды. Ожидаемо: PV ≈ 11498.45, SL_total/SL_critical = 1.000, shortage = 0, потери/throughput 1.2% ≤ 2%, резерв ≥ 55.29 т; 0 hard-нарушений у адаптированного плана. Сверь числа; расхождение — блоккер B-STRESS-NUM.
11. Проверь честность ориентиров: в материалах (scenario_comparison.md, записка, презентация) должен присутствовать и результат НЕадаптированного плана в стрессе (дефицит ~130 т, SL 0.85–0.94) — кейс требует показывать нарушение ориентиров, а не прятать. Отсутствие — блоккер B-HONESTY.

## Шаг 3 — Дополнительные тесты

12. Sensitivity: выполни указанные в README/ИНСТРУКЦИЯ команды (low/high demand, tornado, reverse-пороги). Результаты должны существовать в results/stress/P02_* и совпадать с цифрами записки (выбери 3 числа и сверь). Расхождение — блоккер B-SENS.
13. Реестр рисков: results/risk_register.csv — 10 рисков, у каждого рассчитанные последствия (т/млн/SL), мера и остаток. Пустые или «на глаз» поля — блоккер B-RISK.
14. Геополитический бонус: по README/инструкции запусти гео-сценарий (коэффициент 1.2 к каналу A, 2038–2039), убедись: эффект +ΔPV ≈ +337.9 млн, SL/shortage не меняются; затем «восстановить контрольные цены» — повторный BASE совпадает с исходным (в отчёте WP4 заявлено побайтовое совпадение SHA). Несовпадение — блоккер B-GEO.
15. Расширяемость: по README выполни демонстрацию Source-X и/или 2041 года на КОПИИ набора (не трогая data/). Система должна подхватить новый источник/период без правки кода. Падение — блоккер B-EXT. После демо убедись, что data/ не изменился (git status чист).
16. Невалидный ввод: прогони примеры tests/examples/invalid_plan_examples — ожидаются понятные русские сообщения (rule/период/параметр), НЕ traceback. Иначе — блоккер B-ERRMSG.

## Шаг 4 — Сравнение и выгрузка

17. Сравнение BASE vs STRESS: results/scenario_comparison.md открыт, числа соответствуют шагам 1–2; одностраничное резюме docs/note/RESUME_1page.md существует и не противоречит сравнению.
18. Экспорт: выполни выгрузку FINAL_BASE (CSV и XLSX по инструкции). Проверь: файлы открываются; 5 произвольно выбранных чисел (спрос, поставлено, потери, закупки, резервирование за любой год) совпадают с UI/результатами run_plan; в экспорте есть scenario_id, plan_id, единицы, assumptions_reference. Расхождение — блоккер B-EXPORT.
19. Сохранение/повторное открытие: сохрани изменённый план, закрой, открой заново — результат идентичен (идемпотентность). Иначе — блоккер B-PERSIST.

## Сквозные проверки документов

20. docs/УПРАВЛЕНЧЕСКАЯ_ЗАПИСКА.md: объём 8–12 страниц (оцени по структуре/числу разделов); grep "[[" — ноль непоставленных плейсхолдеров; выбери 3 числа из записки и найди их источник в results/ (трассируемость). Плейсхолдеры или нетрассируемые числа — блоккер B-NOTE.
21. presentation/: 12 слайдов; выбери 2 числа со слайдов и сверь с results/ и запиской. Расхождение — блоккер B-PRES.
22. README: состав команды заполнен (Сычев Алексей, Асанди Максим, Юрийчук Михаил); все внутренние ссылки README ведут на существующие файлы (пройди по каждой). Битая ссылка — блоккер B-README-LINK.
23. docs/ИСТОЧНИКИ.md: библиография с DOI; атрибуция Federgruen vs Han корректна (Federgruen — dual sourcing POM 2022; Han et al. 2023 — Omega 102775). Путаница — блоккер B-CITE.

## Финал

24. Повтори git status в клоне: рабочий каталог должен остаться чистым (ты ничего не менял; временные файлы экспорта/сохранённые планы из шагов 18–19 удали или отметь, что они созданы вне репозитория).
25. Напиши отчёт аудитора (текстом в ответе, НЕ в репозиторий):
    - версия под аудитом (commit, дата);
    - таблица «шаг → ожидание → факт → OK/блоккер» по всем 24 шагам;
    - реестр блоккеров: ID, шаг, что ожидалось, что получилось, воспроизведение (точная команда);
    - время полного прохода (минуты) — это оценка «может ли эксперт пройти по инструкции»;
    - итоговый вердикт: ГОТОВ К СДАЧЕ / НЕ ГОТОВ (список блоккеров) / ГОТОВ С ЗАМЕЧАНИЯМИ (мелочи, не влияющие на проверку).

Правила аудитора: ничего не чинить; не додумывать за инструкцию (если шаг непонятен — это само по себе замечание к README/инструкции); числа сравнивать точно, а не «на глаз»; каждый блоккер обязан содержать команду воспроизведения.
```

## После прогона

Отчёт аудитора присылается оркестратору. При блоккерах — точечные исправления соответствующим WP (не «переделка волны»), повторный прогон только упавших шагов. При вердикте «ГОТОВ» — зеркалирование на GitVerse и сдача.
