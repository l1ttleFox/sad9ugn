# WP4 Волна 1 — Интерфейс оператора на синтетических моках (БЕЗ ядра)

## Роль
Ты — frontend/fullstack разработчик (Python + Streamlit). Строишь рабочее место оператора планирования топливного узла ПРОТИВ контракта `result_format.json`, на синтетических мок-данных. Ядро WP1 ещё не готов — это не мешает: контракт заморожен. Волна выполняется параллельно с WP1.

## Обязательное чтение
1. `ai_workstreams/00_contracts/result_format.json` — схема результата (твой источник правды).
2. `ai_workstreams/00_contracts/plan_format.json` — формат плана (редактор решений).
3. `ai_workstreams/00_contracts/core_api.md` — сигнатуры, которые ты будешь вызывать в волне 2 (сейчас — заглушки-моки).
4. `ai_workstreams/00_contracts/units_and_conventions.md` — единицы для подписей.
5. Постановка (docs/STARTER_README.md §«Функции и качества решения», README организатора): требования к доступности, читаемости, «цвет не единственное обозначение нарушения».

## Задание

### 1. Мок-генератор `app/mock_data.py`
Генерирует синтетические `RunResult` для BASE и MANDATORY_STRESS (правдоподобные, но ВЫМЫШЛЕННЫЕ числа, помеченные `meta.engine_version = "MOCK"`): monthly_balance 72 периода, yearly_balance, source_schedule по 5 каналам, financial_breakdown, constraint_checks (включая 2–3 намеренных нарушения), inventory_trace, risk_register-заглушка. Моки — в `app/mocks/*.json`.

### 2. Интерфейс `app/main.py` (Streamlit, многостраничный)
Навигация (sidebar), страницы:
- **Обзор:** спрос/поставки/запасы/потери/расходы/дефицит по годам; SL_total и SL_critical ОТДЕЛЬНО с единицами и именем сценария; KPI-плитки.
- **Графики:** supply by source (стек), demand vs served, inventory trace с порогом 45 дней и ёмкостью, расходы по годам (стек: procurement/reservation/holding/CAPEX/OPEX), CAPEX timeline против лимитов 1800/2800, SL по годам против 0.97/0.99, BASE vs STRESS дельты.
- **План и контракты:** редактор решений по plan_format.json — заказы по каналам и периодам (таблица + формы), резервирование мощностей, инвестиции (buy_option/exercise/fund_capex с датами), inventory policy, emergency contract. Реестр контрактов: контрагент, объём, сроки, lead time, резервирование, TOP, оплата, правила пересмотра (таблица, редактируемая).
- **Ограничения:** список всех проверок (passed + violated); нарушение = rule_id, период, факт, лимит, excess, сообщение на русском; иконка/цвет/текст (цвет не единственный канал).
- **Сценарии:** переключатель BASE / MANDATORY_STRESS / TEAM_*; кнопка «Пересчитать»; сравнение side-by-side (расходы, SL, запас, дефицит, нарушения) на общей базе.
- **Риски:** таблица реестра с последствиями (т/млн/SL).
- **Сохранение:** save plan → JSON, load plan; export → CSV (в волне 1 — выгрузка моков, структура по export.schema.json).

### 3. Архитектурное требование
Весь доступ к данным — через слой `app/services.py`: `get_run_result(scenario_id, plan) -> dict` (сейчас возвращает мок; в волне 2 — вызывает `run_plan` ядра). НИ одной прямой работы с моками в страницах. Это сделает волну 2 заменой одного файла.

### 4. Валидация ввода
Ошибочный ввод (отрицательный заказ, reserved > capacity, несуществующий канал) — понятное сообщение на русском с именем параметра, до отправки в расчёт (клиентская валидация по ограничениям CASE_INPUT, захардкодить лимиты из data/*.csv — они не меняются).

## Что НЕ делать
- Не реализовывать расчёты (никакой формульной логики в UI — только отображение).
- Не подключаться к несуществующему ядру; `import src.engine` только через services-слой с try/except и fallback на моки.

## Формат результата
- `app/` (main.py, services.py, mock_data.py, mocks/, pages/ или эквивалент), `requirements.txt` обновлён (streamlit с версией).
- `REPORT_wave1.md`: скриншот-описание страниц (текстом), как services-слой будет переключён на ядро, известные ограничения моков.
- Проверка: `streamlit run app/main.py` работает полностью на моках.
- Git: `wp4: UI на моках` → push `wp4-ui`.

## Критерии приёмки
1. Все 7 разделов работают на моках без падений.
2. Нарушения читаемы: правило, период, факт, лимит, причина — текст на русском, не только цвет.
3. Переключатель сценариев меняет все данные страниц (на моках BASE vs STRESS видна разница).
4. Экспорт CSV моков соответствует структуре export.schema.json.
5. Services-слой изолирован: замена моков на ядро = правка одного файла.
