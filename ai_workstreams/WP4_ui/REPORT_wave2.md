# WP4 — отчёт по волне 2 (финальное обновление на FINAL-планах)

Дата: 2026-09-19. Статус: **завершено**. Ветка: `wp4-ui`, основа: актуальный `origin/main` после публикации WP2 (FINAL-планы) и решения D8.

Приёмка выполнена на FINAL-планах WP2 и актуальном ядре `0.3.0-wave3`. Исторические числа предварительного S10 (включая «45 нарушений», порождённые конвенцией «год заказа против года поставки») заменены: конвенция устранена решением D8, мощность проверяется по году физической поставки, FINAL_BASE при открытии имеет 0 hard-нарушений.

## Демонстрационные планы

- Автообнаружение в `results/plans/` находит оба FINAL-файла; кнопки сайдбара:
  - «Загрузить FINAL BASE — FINAL_BASE» → `results/plans/FINAL_BASE.json` (plan_id `FINAL_BASE`, scenario_id `BASE`);
  - «Загрузить FINAL STRESS — FINAL_STRESS» → `results/plans/FINAL_STRESS.json` (plan_id `FINAL_STRESS`, scenario_id `MANDATORY_STRESS`).
- Каждый план открывается в согласованном сценарии (`loaded_scenario_id`).
- Fallback S10 сохранён только на случай отсутствия FINAL и маркируется «предварительный план (FINAL не опубликован)»; сейчас не показывается.
- **FINAL_BASE при открытии: 0 hard-нарушений, SL_total = SL_critical = 1.0 во все годы, дефицит 0 т.** Эскалация WP2 не потребовалась.
- FINAL_STRESS (MANDATORY_STRESS): 0 hard-нарушений, потери ZBO в пределах потолка.

## Интеграция с ядром

- services вызывает только публичный API: `load_case/load_plan/load_scenario/run_plan/export_results/save_plan/load_saved_plan/compare_scenarios`, плюс `apply_scenario_parameters` (адаптер D3.4) и `evaluate_risks` (реестр рисков TEAM_*). Формульной расчётной логики в app/ нет: суммы в `overview_summary` — агрегация полей RunResult для отображения; сравнение BASE↔STRESS выполняет `compare_scenarios` ядра; годовые дельты — разница полей RunResult ядра.
- `USE_ENGINE=True`, `engine_available()` истинно, мок-режим при нормальном запуске не активируется (sidebar: «Расчётное ядро доступно»).
- Полный список constraint_checks (passed и failed) берётся только из `RunResult.checks`; при его отсутствии UI останавливается с явной ошибкой.
- D8.3: `INVENTORY_SHOCK_APPLIED` выделен в информационные записи — метрика «Hard-нарушений» и `violation_count` его не учитывают (проверяется на TEAM_MMOD), в реестре помечается «ℹ️ ИНФОРМАЦИЯ».

## Сохранение и повторное открытие

- «Сохранить в каталог» пишет `results/plans/<plan_id>.json` (через `save_plan` ядра) и рядом `<plan_id>_contracts.json` (D4, внутренний формат UI).
- Повторное открытие восстанавливает план и реестр договоров; все шесть таблиц RunResult (monthly_balance, yearly_balance, source_schedule, inventory_trace, financial_breakdown, constraint_checks) побайтово идентичны исходному расчёту; меняется только plan_id.
- Файлы `*_contracts.json` не попадают в список планов.

## Геополитический модуль

- Событие: канал A, множитель 1.25, период 2038–2039; множитель применяется один раз через `variable_price_multiplier` временного TEAM_GEO-конфига (D8.4).
- Расходы: BASE 12411.71 → событие 13000.70 млн у.е. (Δ +588.99); до/после видны в таблице эффекта.
- «Восстановить контрольные цены» возвращает BASE **побайтово**: канонический JSON identical (SHA-256 префикс 6e4285ecf62148b5ff4361613ce6b4be до и после).
- CASE_INPUT (data/*.csv, configs/*.yaml) не мутируются: SHA-256 всех файлов до и после прогона совпали.

## TEAM-сценарии и риски

- Автообнаруживаются все 10 TEAM YAML (основной `configs/team/`, резервный каталог WP3); все 10 прогоняются ядром на FINAL_BASE.
- Раздел «Риски»: реестр рисков текущего плана считается `evaluate_risks` ядра живьём (10 записей с последствиями в т, млн у.е., долях SL) — устаревшие статические цифры не используются; опубликованный `results/risk_register.csv` WP3 показывается отдельной таблицей, когда доступен.
- INVENTORY_SHOCK_APPLIED не показывается как hard-нарушение (см. выше).
