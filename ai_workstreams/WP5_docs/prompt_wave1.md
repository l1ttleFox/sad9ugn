## Задание — создать `docs/note/` (записка по частям)

1. **`00_structure.md`** — оглавление записки с бюджетом страниц (8–12 стр.): резюме (0.5), проблематика и цель (0.5), архитектура расчёта (1.5), данные и допущения (1), сравнение стратегий (2), контракты и инвестиции (1.5), стресс-тесты и риски (2), стейкхолдеры (1), бюджет и roadmap (1), ограничения модели (0.5), источники (0.5+приложение).
2. **`01_architecture.md`** — логика архитектуры расчёта: данные → решения → поставки → баланс → сервис → расходы → ограничения → риски → выбор. Для каждого блока: входы, выходы, формулы (из CALCULATION_RULES — цитировать точно), источник метода, границы применимости. Разделить концептуальную модель и программную реализацию (core_api.md). Схема mermaid.
3. **`02_data_assumptions.md`** — таблица всех параметров: CASE_INPUT (источник — файлы data/), TEAM_DECISION (что выбирает оператор), TEAM_ASSUMPTION (реестр TA-01…TA-09 с обоснованиями). Для каждого TA: смысл, единицы, диапазон, статус (требование кейса «допустимая кастомизация»).
4. **`03_methods_evidence_map.md`** — таблица «источник → положение/метод → реализация в модели → ограничение применимости» для всех 8+3 источников (организаторские + наши). Включить: Federgruen (пороговые политики dual sourcing), Han (robust/Γ, ε-constraint Парето), Guo (capacity reservation = virtual inventory; запасы мостят lead time), Linkov (MCDA swing-weighting, adaptive management), Simonini (физика boil-off, ZBO-демонстратор RRM3), Sommariva (WACC 11.5–13% → наша ставка 10%, экономика Луна/Земля 2:1), Ho (network flow + inventory control как класс модели), Tanaka (гейты, опционы, закон необходимого разнообразия). Библиография с DOI. Отделить материалы постановщика от самостоятельно найденных.
5. **`04_contracts.md`** — контрактно-финансовая архитектура: по каждому каналу — контрагент (условный), объём, сроки/lead time, резервирование, TOP, оплата, ответственность, правила пересмотра; опцион Earth-New (90+270) как реальный опцион; инвестиционные ворота (decision gates): G1 (2035: старт A/B + покупка опциона C?), G2 (2036–2037: ZBO), G3 (до 2037-12: финансирование ISRU), G4 (2038: exercise C по факту ISRU); распределение рисков между оператором и поставщиками; структура финансирования (ГЧП/проектное финансирование по Sommariva/Tanaka — как опция, помечена TEAM_ASSUMPTION).
6. **`05_stakeholders.md`** — карта сторон: оператор, критические потребители, коммерческие потребители, поставщики топлива/запуска (по каналам), финансирующая сторона. Для каждой: интересы → показатели (KPI) → обязательства → кто несёт затраты и риски → как меняется баланс при стрессе (структура, числа — волна 2). MCDA-рамка выбора (Linkov): критерии, нормализация, происхождение весов, правило изменения; запрет «улучшать оценку снижением веса пострадавшей стороны».
7. **`06_kpi.md`** — KPI надёжности и экономики с формулами, целями, способом контроля: SL_total/SL_critical, reserve coverage days, losses/throughput, cost per served ton, PV расходов, CAPEX headroom, TOP burn (переплата сверх отбора), время реакции (lead times).
8. **`07_limitations.md`** — ограничения модели: агрегированность (нет разделения LOX/LH2), детерминированный BASE, месячный шаг, reliability вне BASE, учебные цены (не реальные), что НЕ моделируется (траектории, CFD, телеметрия).
9. **`08_geopolitics_bonus.md`** — описание бонусного модуля: причинная цепочка «событие → параметр цены → расходы и решения», пример условного сценария (торговые ограничения → коэффициент к цене канала A → пересчёт → эффект на стороны), оговорки (условные сценарии, не прогноз политики; рыночная цена топлива ≠ агрегированная цена доставки).
