# P02 — чувствительность

## Цель и диапазоны

По одному фактору, затем для существенных пар факторов, найти устойчивость **одного плана**. Контроль — BASE. Точки low/high total demand берутся из `data/demand.csv` (2035: 80/110; 2036: 112/154; 2037: 152/209; 2038: 200/312.5; 2039: 256/400; 2040: 312/487.5 т). Для критического спроса отдельные low/high данные не заданы: сохранять долю base_critical/base_total внутри года как **предложение допущения**, до принятия оркестратором не выдавать результат за CASE_INPUT. Не применять эти точки к mandatory stress автоматически.

Остальные оси: переменная цена A/B ×0.8/1.0/1.2 (испытательный ±20%, TEAM_ASSUMPTION для согласования); фактическая доля D 0.40/0.55/0.75/1.0 по 2038–2039 (0.55/0.75 — CASE_INPUT только в mandatory, прочие — испытательные); ставка PV 0.05/0.10/0.15 (0.10 — TA-06, границы для сравнения альтернатив, физические метрики не зависят); lead C 18/24 месяца (CASE_INPUT диапазон, 24 — TA-02); exercise C — исходная дата плана и сдвиги ±6/12 месяцев, только в допустимых датах опциона. Сдвиг решения оформлять копией плана.

## Результат и граница

Tornado-таблица: фактор, исходное/нижнее/верхнее значение, ΔTotalCost и ΔPV (млн), Δдефицит (т), ΔSL (п.п.), изменение нарушений, источник точки. Для каждого порога искать ближайшее значение, где впервые нарушаются сервис, резерв, CAPEX, мощность или экономика выбранного критерия. Для монотонной оси уточнять бинарным поиском до 0.01 млн/т, 0.01 т, 0.01 п.п. или 1 месяца; при немонотонности — сетка. Формулировать «план ломается при цене A > X» только если цена действительно связана с проверяемым лимитом; без бюджетного лимита цена одна не делает план недопустимым.

## Общая процедура

1. Зафиксировать SHA входа, `plan_id`, исходный JSON плана, `scenario_id`, версию ядра, дату результата и seed только если есть случайность. Взять **один и тот же план** для BASE и исследовательского прогона. Если нужна адаптация, сохранить её как отдельный план и не приписывать её эффект окружению.
2. Запустить `load_case(data/)`, `load_plan(...)`, `load_scenario(...)`, затем `run_plan(case, plan, scenario)`. Для расширенных `scenario_parameters` создать копию CaseData/Plan, проверить исходные значения и применить ровно один описанный override до прогона; при отсутствии такого адаптера отметить тест как неисполненный.
3. Сохранить годовые/месячные `Q_delivered`, `Losses`, `I_start/I_end`, дефицит, SL_total/critical, расходы по статьям, CAPEX, PV и весь violation list. Проверить баланс и расхождение с BASE в т, млн у.е. и п.п. SL. Запрещён автоматический множитель reliability.

## Критерии нарушения

В BASE: годовой SL_total <0.97, SL_critical <0.99, январский запас < D_y×45/365, отрицательный/сверхъёмкий месячный запас, CAPEX >1800 до 2037 или >2800 до 2040, нарушение доступности/мощности, TOP или запрета E как базового >2 лет. В исследовательском стрессе те же границы показываются как нарушения устойчивости; потолок losses/throughput ≤0.02 действует только там, где он явно включён. Деление при нулевом throughput помечать «не определено», не подставлять ноль.
