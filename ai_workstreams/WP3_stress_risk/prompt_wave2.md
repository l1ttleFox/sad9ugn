# WP3 Волна 2 — Расчёт стресс-тестов и рисков на ядре

## Роль
Ты — аналитик рисков. Ядро WP1 готово, финальная стратегия WP2 выбрана. Прогоняешь протоколы волны 1 на ядре, наполняешь реестр рисков рассчитанными последствиями, готовишь материалы для критериев 10–16 жюри (35 баллов).

## Зависимости
- Ветки `wp1-core` (ядро) и `wp2-strategy` (FINAL-планы `results/plans/FINAL_*.json`).
- Свои материалы волны 1: `protocols/`, `risk_register.yaml`, `configs/team/`.

## Задание
1. **P01 Обязательный стресс:** прогон FINAL-плана в MANDATORY_STRESS. Декомпозиция эффекта: отдельно вклад спроса ×1.15, цен ×1.25, ISRU 55/75%, потолка потерь (промежуточные TEAM-тесты по одному фактору — кейс требует «покажите, какие эффекты вызваны чем»). Таблица: год / SL_total / SL_crit / shortage / потери / расходы — BASE vs STRESS vs декомпозиция.
2. **P02 Чувствительность:** low/high demand для FINAL-плана; вариации цены A/B ±20%, ставки 5/15%, lead time C 18/24. Tornado-таблица влияния на PV и SL. Пороги: при каком значении параметра план впервые нарушает каждое ограничение (reverse-границы).
3. **P04 Reverse stress:** grid-поиск ломающей комбинации (спрос × цена A × доля ISRU); карта области исполнимости; «план умирает при …» — конкретные числа.
4. **P03 TEAM-риски:** прогон каждого сценария из risk_register через ядро; для каждого риска: физическое последствие (т), финансовое (млн у.е.), сервисное (пункты SL, годы нарушения); меры (mitigation) — пересчитать с мерой (например, +резерв B, досрочный exercise опциона) и показать остаточный риск. Стоимость каждой меры.
5. **Бонус P05 Геополитика:** реализовать TEAM_GEO_CHANNEL_A как работающий модуль: event → коэффициент цены канала → пересчёт → эффект на расходы/SL/стороны; экспорт параметров события; восстановление контрольных цен (проверить: повторный прогон = исходные числа). Совместный тест с MANDATORY_STRESS — только как отдельный явно объявленный combined-сценарий с правилом «эффект не начисляется дважды».
6. **Финальный risk_register:** `results/risk_register.csv` (+md) — все поля README §22 заполнены, последствия РАССЧИТАНЫ ядром (не порядки «на глаз»); probability_basis — диапазон/сценарий с обоснованием.
7. **Адаптация:** для рисков с триггерами (ISRU delay, ZBO failure) описать: какие решения приняты заранее, какие после наблюдения, время реакции (lead times!), стоимость и пределы адаптации — требование кейса «если стратегия предполагает реакцию на события».
8. **Seed/воспроизводимость:** если где-то есть случайность — seed и настройки в meta.

## Что НЕ делать
- Не менять CASE_INPUT и MANDATORY_STRESS; не объединять стрессы молча; не выдавать произвольные сценарные частоты за вероятности.
- Не менять ядро (баги → REPORT).

## Формат результата
- `results/stress/` — таблицы и выгрузки по каждому протоколу; `results/risk_register.csv`; `results/geopolitics/` (бонус).
- `REPORT_wave2.md`: ключевые числа для записки (WP5 заберёт отсюда): эффект стресса по годам, топ-3 риска с последствиями, пороги reverse-stress, результат гео-модуля.
- Git: `wp3: стресс-расчёты и реестр рисков` → push `wp3-stress`.

## Критерии приёмки
1. Обязательный стресс применён точно по yaml (проверить множители по годам); 55/75% не умножены на reliability (показать в отчёте).
2. Каждый риск реестра имеет рассчитанное последствие в т/млн/SL и меру с остаточным риском.
3. Reverse-границы конкретны («SL_crit<0.99 в 2039 при цене A ≥ X млн/т»).
4. Гео-модуль: до/после сравнение, экспорт, восстановление цен — всё работает.
5. Все выгрузки совпадают с числами ядра.
