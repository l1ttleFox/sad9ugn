## Задание

### 1. Протоколы обязательных тестов (`protocols/`)
Для каждого теста: цель, изменяемые параметры и их происхождение (CASE_INPUT / TEAM_ASSUMPTION с обоснованием), сохраняемые условия, исследуемый план, метрики, критерий нарушения, способ воспроизведения (требование кейса «Методики стресс-тестирования»):
- `P01_mandatory_stress.md` — точный протокол: ×1.15 спрос с 2038 (общий И критический), ×1.25 цены A/B только 2038–2039, ISRU 0.55/0.75 фактические доли (БЕЗ повторного умножения на reliability), потолок потери/throughput ≤2% с 2038. Анти-паттерны: не складывать с high-demand автоматически; один шок не учитывать дважды.
- `P02_sensitivity.md` — какие параметры варьируем и в каких диапазонах с обоснованием: low/high demand (CASE_INPUT точки); цена A/B ±20%; доля ISRU в поставках; ставка дисконтирования 5–15%; lead time C 18/24; момент exercise опциона. Формат результата: tornado-таблица + пороги нарушения (reverse-границы: «план ломается при цене A > X»).
- `P03_team_risks.md` — сценарии из реестра рисков (ниже).
- `P04_reverse_stress.md` — методика поиска комбинации условий, ломающей план (цель: найти границу по спросу/цене/недопоставке; grid-поиск по 2–3 осям).
- `P05_geopolitics.md` — протокол бонусного модуля: event → коэффициент к агрегированной цене канала → пересчёт → эффект; обязательны экспорт параметров и восстановление исходных цен; правило сочетания с mandatory stress (эффект не начисляется дважды).

### 2. Реестр рисков (`risk_register.yaml` + `risk_register.md`)
Формат полей — README организатора §22 (risk_id, event, cause, affected_parameter, period, probability_basis_or_range, physical/financial/service_consequence, dependencies, owner, mitigation, residual). Минимум 8–10 рисков, специфичных для НАШЕГО плана (критерий 14: не «общие риски космонавтики»!):
- недопоставка ISRU сверх стресса (0.55→0.40 сценарий);
- срыв ввода ISRU на 12 мес (commissioning 2039) — TEAM-сценарий (вопрос В3);
- отказ ZBO-криокулера → возврат потерь к 4.5% (нарушение потолка в STRESS);
- MMOD-пробой хранилища → потеря части запаса (порядок — по ответу эксперта В2 или интервально);
- рост цены Emergency >13.8 при активации (спот-волатильность);
- задержка exercise Earth-New → мощность не успевает к пику 2039;
- превышение CAPEX-сметы ISRU (+15%) → ломает лимит 1800 (запас всего 10–370!);
- провайдер A снижает мощность (геополитика/производство) — связка с бонус-модулем;
- тепловой режим/деградация MLI → рост потерь базового хранения.
Для каждого: КАК он маппится на вход модели (какой параметр какого файла/сценария меняется) — чтобы волна 2 просто прогнала это через ядро. Вероятности: только обоснованные (диапазон/сценарий честнее выдуманной точки — STRESS_PROTOCOL).

### 3. Машиночитаемые TEAM_*-сценарии (`configs/team/`)
YAML по формату scenario.schema.json: TEAM_ISRU_DELAY, TEAM_ZBO_FAILURE, TEAM_MMOD, TEAM_CAPEX_OVERRUN, TEAM_PRICE_SPIKE_E, TEAM_GEO_CHANNEL_A (бонус). Каждый с notes: что изменено, основание, правило изоляции (не смешивать с MANDATORY_STRESS без явного combined-сценария).

### 4. Монте-Карло — решение «делать/не делать»
Обосновать: при отсутствии статистики отказов кейс прямо предпочитает сценарно-интервальный подход. Если всё же МК — раскрыть распределения (логнормаль по Sommariva σ=10%), число испытаний, seed, точность. Рекомендация: ограничиться детерминированными TEAM-сценариями + grid reverse-stress; МК — опциональное расширение.

## Критерии приёмки
1. Каждый протокол самодостаточен: другой человек/ИИ может повторить тест без устных пояснений.
2. Каждый риск реестра имеет машиночитаемый mapping на вход модели и хотя бы одну количественную оценку последствия (в тоннах или млн у.е. — порядок, формула расчёта в волне 2).
3. TEAM_*-сценарии валидны против scenario.schema.json (проверить скриптом).
4. Обязательный стресс НЕ смешан с собственными сценариями.
